# Kurage 申請書オートフィル（kfillout）

申請書の **Word / Excel** を上げると、空欄を見つけて**分かるところだけ**を埋め、
**元の書式のまま**返す。`:18354`

## なぜ作るか（2026-09-14 実測）

名古屋市が配っている申請様式は **4,024件**。市の「申請・手続き検索」に埋め込まれている
公開データを集計した内訳:

| 様式の形式 | 件数 | 割合 |
|---|---:|---:|
| Word | 1,652 | 41.1% |
| PDF | 1,230 | 30.6% |
| Excel | 367 | 9.1% |
| 外部サイト | 775 | 19.3% |

**ダウンロードして書くオフィス文書が 80.8%。オンラインで完結できるのは 26.9%**（1,084件）。
窓口しか無い様式が 591件。127課・698ページに散っている。

さらに分野別で見ると、**窓口へ行くのがいちばん大変な人の手続きほどオンライン化されていない**:

障害福祉 18.8% ／ 介護保険 25.4% ／ 子育て・妊娠・出産 26.8% ／ 高齢者福祉 28.2%
（対して 国民健康保険・国民年金 42.4%、医療・薬務 41.8%）

## 既存サービスとの違い

海外には同種のサービスがある（Instafill.ai / pdfFiller AI / Filly AI / AutoFillPDF / DocHub）。
ただし**多くは PDF に変換してから埋めるので様式が変わる**。日本の行政・研究機関は
「この様式で」と指定するため、それでは提出できない。

ここは **.docx / .xlsx の文字だけを差し替える**ので、表・余白・ページの形が保たれる。

## AIに文章は作らせない

入る文字は次の3つだけ。

1. **日付** … 申請日は今日。様式が「令和○年」なら和暦、「2026年○月○日」なら西暦
2. **よく使う情報** … 会社名・所在地・代表者など、一度入れた値（`data/profile.json`）
3. **利用者の入力** … その申請だけの値（サービス名・用途など）

AI がするのは「この空欄はどの項目か」の見分けだけ。当てはまらない欄は**空のまま残して画面に出す**。
申請書で作文されると事故になる。判定に使う LLM はローカル（Ollama 192.168.0.3・gemma4）なので、
ファイルも会社情報も外部のAIサービスへ出ない。

## 実装で踏んだ罠

- **商号の位置**: 様式「〇〇株式会社」に「株式会社エクスブリッジ」を入れると
  「エクスブリッジ株式会社」という**別の法人名**になる。法人格の位置が違うときは
  様式の法人格ごと置き換える（`app/fill.py` `_company_for`・`tests/test_fill.py`）
- **ランの分割**: Word は1段落を複数の `<w:r>` に割るので、ランを単体で見ると空欄が見つからない。
  段落単位で組み立てて探し、書き戻すときにランへ配り直す（`app/forms.py`）
- **LLMを使う経路と使わない経路で結果が変わる**: ダウンロード時は `use_llm=False` で呼ぶので、
  商号の位置合わせを LLM 分岐の中でやると効かない。共通の最終処理に置く
- **gemma4 は思考型**なので `"think": false` が要る（指定しないと応答が空になる）

## 構成

```
app/forms.py    空欄の検出と、書式を壊さない差し替え（docx / xlsx）
app/profile.py  よく使う情報（会社名・所在地・代表者…）の保存
app/llm.py      「この空欄はどの項目か」の判定（ローカルLLM・文章は作らせない）
app/fill.py     空欄→値を決める。日付／プロフィール／利用者入力の3つだけ
app/main.py     画面とAPI
```

## 動かす

```bash
systemctl --user start kfillout        # :18354
curl http://127.0.0.1:18354/healthz
.venv/bin/python -m pytest tests/ -q
```
